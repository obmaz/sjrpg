# AI 개발 지침 · 3D판

이 파일은 `sjrpg_3d/`에 적용됩니다. 이 프로젝트에서는 실제3D 물리·지형·배우가 공간의 기준이며 기존2D 노드는 UI·진행·원화 호환 어댑터입니다. 카메라는120° 직교 쿼터뷰를 유지하고 입체 에셋이 없는 대상은 개별2.5D 원화를 재사용합니다. 기준2D판인 `../sjrpg_2d/`는 별도로 보존합니다. 작업 전에 [README.md](README.md)로 현재 이식 범위를,
[docs/development.md](docs/development.md)로 구조·데이터 출처·검증 방법을 확인합니다.
문서는 탐색용이므로 변경 전에는 실제 코드를 읽습니다.

## 프로젝트

- Godot 4.7.2 프로젝트(GL Compatibility)이며 GitHub Pages(`/sjrpg/`)에 웹(WASM, 단일 스레드)으로 배포합니다.
  엔진·템플릿 버전 기준은 `.godot-version`이며 로컬 도구와 CI가 같은 파일을 읽습니다.
  현재 `obmaz/sjrpg`는 Godot 저장소입니다. 기존 Flutter·Bonfire판 소스는 **참고 자료**입니다. 세계관·전사와 마법사·쿼터뷰는 유지하되
  Godot판의 조작감·가독성·진행을 우선해 규칙·밸런스를 개선합니다. 원본과 다른 규칙은 README와 관련 코드에 이유를 남깁니다.
  현재 목표는 숲 1장 완성(탐험 보강·선택형 동굴 포함)이며, 후속 지역과 탈것은 이후에 작업합니다.
- 스크립트는 `scripts/`, 데이터는 `assets/data/`, 원화는 `assets/art/`, 테스트는 `tests/`, 도구는 `tools/`입니다.
  장면(`scenes/`)은 `main.tscn` 하나이며 화면은 코드로 구성합니다.

## 그림 규칙 (가장 중요)

- **3D 모델·재질은 [루트3D 에셋 제작 기준](../docs/3d-asset-guide.md)을 먼저 읽고 따릅니다.** 실제 미터 단위 기하·전체 면·법선·UV·광원·충돌·모바일 화면을 검수합니다. 절차적 제작도 실제 부피와 재질을 가진 메시 모델링에는 사용할 수 있습니다. 아래2D 원화 규격은 입체 자산이 없는 개별 카드의 제작에만 적용하며3D 구조의 검수를 대신하지 않습니다. `../sjrpg_2d/`는 동결되어 있으므로3D 개선을 복사하거나 수정하지 않습니다.

- **2D 카드·UI 원화 생성 전 필수**: [레퍼런스 분위기 제작 가이드](../sjrpg_2d/docs/reference-look-guide.md), [아트 기준](../sjrpg_2d/docs/art-direction.md), [공통 생성 프롬프트](../sjrpg_2d/docs/art-prompts.md)를 읽습니다. `assets/source/style/approved-game-reference.jpg`가 사용자의 최상위 스타일 기준입니다. 생성 도구에 이 화면과 같은 패밀리의 검수된 원화를 실제 참조 이미지로 첨부합니다. 성문·성벽처럼 연결되는 자산은 통합 컨셉으로 재료·줄눈 크기·띠장·흉벽 비례를 먼저 맞추고 양 방향과 코너까지 같은 패밀리를 사용합니다. 생성 프롬프트·실제 참조 파일·채택한 원본·실측/해시는 해당 제작 문서에 보존합니다. 생성 컨셉을 사용자 승인으로 간주하거나 각도 실측을 대신하게 하지 않습니다.

- **2.5D 쿼터뷰 120°**: 지면 두 축은 ±30°, 수직은 90°입니다(`scripts/iso.gd`).
  바닥 접점이나 구성한 충돌 사각형만으로 원화가 맞다고 판단하지 않습니다. 모든 직선 구조물은 실제 원화의 상·중·하단,
  두 방향·마주보는 모서리를 측정합니다. 렌더링 후 각도 오차와 같은 축의 평행선 간 차이 모두 2.5° 이내여야 합니다.
  `tools/extract/art_axis_measure.json`에 실제 픽셀 선분을 기록하고, 원화·아틀라스 해시를 명시적으로 갱신합니다
  (`art_audit_catalog.py`). `art_projection`은 실제 그리기 투영·선분 내부·메시 뒤집힘·해시를 검사합니다.
  `axis`는 배치·충돌 모델 검사이며 원화 검증을 대신하지 않습니다. 지붕 경사·계단 진행 방향·자연 실루엣은 수평축과 구별합니다.
  새 원화는 [측정·재생성 방법](../sjrpg_2d/docs/chapel-regeneration.md)을 따릅니다.
- HUD·팝업은 사용자가 승인한 최종 구도를 따릅니다([docs/ui-reference.md](../sjrpg_2d/docs/ui-reference.md)). 상태창·스킬 부채꼴·조이스틱·하단 메뉴 비율과 얇은 청동/은색 테두리를 유지하고, 큰 단색 원·글자 대체 공격 아이콘·밝은 노란 버튼으로 되돌리지 않습니다.
- 2D 카드 원화는 코드 도형으로 대신 그리지 않습니다. 실제3D 모델은 부피·법선·UV·재질·충돌을 가진 메시로 제작하며 절차적 모델링도 루트3D 제작 기준에 따라 사용할 수 있습니다. 2D 원화 프롬프트를 정면3D 알베도 생성에 적용하지 않습니다.
- 3D판 텍스처는 `assets/data/texture_policy.json`과 `tools/texture_policy.py`를 따릅니다. 지정한 불투명 월드 표면은 VRAM 압축(2, S3TC/ETC2)을 사용하고, UI·효과·투명 잎·유리·현재 배우 텍스처는 기존 손실 압축(1)과 알파/밉맵 설정을 보존합니다. 임의 리사이즈나 일괄 GPU 변환을 하지 않습니다. `tools/import_project.sh`로 정책 적용→Godot 재임포트→검증을 수행하며 최종 Web PCK와 실제 모바일 화면을 확인합니다. APK 빌드·패키지 검증은 아래 APK 실행 정책에 따라 사용자 명시 요청 시에만 수행합니다. 2D판은 동결합니다.
- 그림·UI를 바꾸면 실제 브라우저 화면(`tools/screenshot.mjs`)으로 가로·세로를 함께 확인합니다. 헤드리스 테스트 통과로 시각 검증을 대신하지 않습니다.

## 데이터 출처

- `assets/data/{skills,gear,village,landmarks}.json`은 원본 Dart에서 `tools/extract/extract_data.py`로 뽑습니다. 손으로 고치지 말고
  추출 스크립트를 고쳐 다시 만듭니다(재현 가능해야 함). 추출 후 `git diff`로 의도한 변화만 있는지 확인합니다.
- 전투 수치(피해·체력·소모·가격)는 원본 단위를 따릅니다: 정수 내부 단위, 화면 표시는 체력·피해 ×100, 자원 ×10(`HudArt.stat/res`).
  Godot판 조정값은 추출 JSON을 직접 바꾸지 않고 별도 설정으로 적용합니다. 변경한 규칙과 이유를 주석과 README에 적습니다.

## GDScript 규칙

- 탭 들여쓰기, 가능한 곳에는 타입을 적습니다. `Dictionary`/`Variant`에서 꺼낸 값은 `var x: float = d["x"]`처럼 타입을 명시합니다
  (`:=`로 추론하면 "Variant로 추론" 경고가 오류로 처리됩니다). 한 줄 람다 안에서 `match`를 쓰지 말고 함수로 뺍니다.
- 폰 화면: 세로 720×1280, 가로 1280×720 기준 해상도입니다(`main.gd`). 패널은 `PanelFrame`을 쓰고(안전 영역, 64px+ 터치, 큰 글자),
  일반 화면의 `UiKit` 글자 크기는 `PanelFrame`이 `UiKit.boost`로 키웁니다.
- 게임플레이 상태는 `GameState`(자동 로드)에 두고 `save_game()`/`load_game()`에 항목을 추가합니다. 저장은 하위 호환(`data.get(키, 기본값)`)을 지킵니다.
- 효과음(`SoundFx`)·진동(`Prefs.pulse`)은 설정에서 꺼질 수 있으므로 항상 해당 호출을 거칩니다.
- 사용하지 않는 코드·자산은 지웁니다. 주석은 현재 동작의 이유·단위·불변 조건을 설명합니다.

## 검증과 완료

변경 후 반드시 실행합니다.

```sh
tools/check.sh                 # 임포트(스크립트 오류) + 전체 테스트
tools/check.sh --only=quests   # 일부 케이스
tools/check.sh --export        # 웹 빌드까지
```

- 새 기능은 `tests/cases/`에 케이스를 추가합니다(`extends TestCase`, `run()` 구현). 실패는 `check()`/`failures += 1`로 남깁니다.
  게임 장면은 `await make_game()`으로 만들고, 걷기·프레임 대기는 `_walk`/`_frames`를 씁니다.
- UI·입력·렌더링을 바꾸면 `tools/export_web.sh` → `tools/serve.sh` → `node tools/screenshot.mjs --scene … --device phone|desktop`으로 화면을 확인합니다.
- **“배포”의 기본 의미는 Dropbox APK 전달**입니다. 웹 배포는 사용자가 별도로 명시한 경우에만 수행합니다. 일반 푸시·APK 배포는 GitHub Pages를 갱신하지 않습니다. 웹 워크플로는 검사와 빌드만 자동 수행하며, 공개 배포는 명시적 요청 후 workflow_dispatch의 publish=true로만 실행합니다.
- 웹 배포를 명시적으로 요청받은 경우에만 해당 커밋의 Pages 배포 성공과 공개 페이지 로드까지 확인합니다.
- 브랜치는 만들지 않고 `main`에 직접 커밋합니다(사용자 지시). 커밋 메시지는 변경의 이유를 적습니다.
- 기능이 바뀌면 README의 사용자 안내와 `docs/development.md`의 구조를 함께 갱신합니다. 일회성 완료 기록은 문서에 쌓지 않습니다.

- 지침과 스킬은 한국어로 작성합니다. 명령어·경로·API 식별자는 원래 표기를 유지합니다.

## APK 빌드와 Dropbox 전달

- 빌드 전에 Dropbox의 `/앱/sjrpg/latest-build.json`을 읽어 다음 `versionCode`를 정합니다. 후속 전달 이력까지 확인해 기존 번호보다 반드시 크게 만들며, 기준 파일을 읽지 못하면 번호를 추정하거나 빌드하지 않습니다. 세부와 JSON 형식은 APK 전달 스킬을 따릅니다.

- APK 빌드·재빌드·Dropbox 업로드는 사용자가 명시적으로 요청했을 때 수행하며, 단순히 “배포”라고 요청한 경우도 Dropbox APK 전달 요청입니다. 일반 개발·리뷰·검증·푸시·웹 배포에 APK 빌드를 추가하지 않습니다.
- [APK 전달 스킬](../.agents/skills/dropbox-apk/SKILL.md)을 따릅니다. 로컬에서 빌드하고 연결된 Dropbox 플러그인으로 전달합니다. 직접 API·별도 업로드 스크립트·환경변수의 Dropbox 자격 증명으로 우회하지 않습니다.
- 사용자가 지정한 기본 폴더는 `/앱/sjrpg`입니다. 스킬의 파일명 규칙에 따른 APK를 전달하고 버전 기록은 `latest-build.json` 한 개만 관리하며 같은 요청에서 목적지 확인을 반복하지 않습니다. 실제 모호함·이름 충돌은 확인합니다.
- GitHub Actions·공개 릴리스·태그·공유 링크·웹 배포는 APK 전달 요청만으로 추가하지 않습니다. 별도로 요청받았을 때만 수행합니다.
- 성공한 빌드와 필요한 검증을 확인한 뒤 업로드하며, 완료 응답의 실제 경로·크기와 기기 실행 여부를 보고합니다. APK만 전달되고 `latest-build.json` 갱신이 실패했다면 구분해 보고합니다.
- 기본 대상은 `sjrpg_3d/`이며 `sjrpg_2d/`는 동결 상태를 유지합니다. 빌드 명령과 Android 도구 버전은 스킬 및 3D판 Android 문서를 따릅니다.
