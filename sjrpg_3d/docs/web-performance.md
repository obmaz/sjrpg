# 웹 성능과 에셋 예산

## 측정 범위

숲 1장과 기존 동굴의 실제 3D 웹 빌드를 대상으로 한다. 기준 소스는 `f3fa9f32caa0cfde08f8f1627431816bde01e00f`, 최적화 소스는 `56bc68b564f9f0e5e1d6da40154aa29ead4d87e8`이다. 2D 프로젝트는 변경하지 않는다.

측정값은 서로 구분한다. PCK는 다운로드 파일 크기이며, RGBA8 예산은 이미지가 해제·압축 없이 모두 동시에 올라갔을 때의 산술값이다. Godot 텍스처 모니터는 엔진의 할당 집계이며 브라우저 전체 RSS나 드라이버의 물리 VRAM 실측이 아니다. WASM 메모리 용량은 사용량의 최고점 이후 유지될 수 있으므로 이것만으로 누수를 판정하지 않는다.

## 실제 에셋 분석

[원본 예산 JSON](../assets/source/performance/baseline-asset-budget.json)은 실제 Godot4.7.2 내보내기 PCK를 파싱한 결과다. [감사 실행](https://github.com/obmaz/sjrpg/actions/runs/42394117139)과 `tools/perf/asset_budget.py`로 재현한다.

| 항목 | 측정 |
| --- | --- |
| 실제 3D PCK | 31,365,964B, 29.91MiB, 506항목 |
| 내보낸 이미지 | 94개 |
| 이미지 전체 동시 RGBA8 산술 예산 | 451,886,848B, 약431MiB |
| 제작용 assets/source의 실제 PCK 포함 | 0항목, 0B |
| 새 선택 화면 일러스트 3장의 실제 PCK 항목 합 | 289,440B |
| 같은 일러스트 3장 전체 동시 RGBA8 산술 예산 | 약18MiB |

제작용 원본 약177MiB는 `assets/source/.gdignore`로 임포트에서 제외되며 실제 PCK에도 없다. 이를 삭제해도 실행 메모리 문제를 해결하지 못한다. 새 선택 화면도 파일 크기만으로 주원인이라고 판단할 근거는 없다.

반면 숨겨진 이전2D 배우가 프레임 정보를 읽을 때 텍스처까지 즉시 로드하고 정적 캐시에 보관했다. 전사/마법사 이동·공격 시트는 장당2048², 몬스터 시트도 종별 약12~20MiB의 RGBA8 예산을 가진다. 실제3D 표시만 쓰는 동안 이 이미지들은 불필요하다. 메타데이터와 텍스처 로딩을 분리하고 실제2.5D 그리기 소비자가 요청할 때만 로드한다. 보이지 않는 Sprite의 피격 효과 동기화도 텍스처를 요청하지 않는다. 원화를 쓰는 대체 표시 경로는 유지한다.

마법사 GLB는18,640삼각형/13프리미티브, 상인은17,612/8이다. 미라는 별도 여성 Ranger 모델로17,595삼각형/5프리미티브이며 GLB2,280,092바이트다. 신규 색 텍스처는512px 네 장과256px 눈 한 장이다. 전체 mip을 RGBA8로 계산한 이미지 예산 상한 추정은5,941,924바이트(약5.67MiB)이며 실제 GPU 할당·PCK 증가량·기기 FPS와 구별한다. 정확한 입력/출력 해시는 `assets/source/native-residents/mira/provenance.json`에 보존한다. 프리미티브 수를 실제 드로콜 수로 간주하지 않는다. 동일 바이트의 일부 표면 텍스처와 약23MiB RGBA8 예산의 마을 시트는 추가 검토 대상이지만, 재질 연결과 실제 사용을 확인하지 않고 일괄 축소하거나 삭제하지 않는다.

공유 마을 석재 교체는 기존 한 텍스처 슬롯을 사용합니다. 런타임 WebP는768×768·194,962바이트이며 전체 mip의 RGBA8 상한 추정은3,145,720바이트입니다. 원본3,076,864바이트 PNG는 `.gdignore`로 게임 임포트/번들에서 제외합니다. 공유 슬레이트도 기존 슬롯을 교체하며768×768·102,152바이트입니다. 전체 mip의 RGBA8 상한 추정은 같은3,145,720바이트이고2,236,328바이트 원본 PNG는 번들에서 제외합니다. 목재·나무껍질은 바이트가 바뀌지 않았습니다. 네 주택은 실제11,420/9,680/7,700/10,480삼각형·각5서피스이며 전체39,280삼각형입니다. 성벽/탑의 정적 두 재질 묶음은 유지하고 움직이는 문짝은 기존처럼 별도입니다. 이 기하/파일 수치는 실제 기기 프레임률이나 브라우저 메모리 실측과 구별합니다.

## 런타임 결과

같은 고품질 설정·마법사·진입 위치에서 실제 시작/저장/설정/동굴 진입 버튼을 사용한다. 기준 실행과 수정 실행의 동일 단계를 비교한 Godot 텍스처 집계는 다음과 같다.

| 단계 | 기준 B | 수정 B | 감소 |
| --- | ---: | ---: | ---: |
| 첫 마을 진입 | 367,197,172 | 253,748,600 | 113,448,572B, 약108.2MiB / 31% |
| 첫 동굴 진입 | 396,206,694 | 266,112,990 | 130,093,704B, 약124.1MiB / 33% |
| 동굴 후 선택 화면 복귀 | 317,185,446 | 187,091,742 | 약124.1MiB / 41% |

[동일 경로 검증 실행](https://github.com/obmaz/sjrpg/actions/runs/42395730787)의 before와 after 작업 모두 각각2프로필·31단계·오류0으로 통과했다. DPR1에서 마을/동굴/복귀를3회 반복하고 화면 회전을 수행했으며 DPR2에서도 전체 경로를 수행했다. 초기 측정 하네스의 샘플 오류는 수정 후 재검증했다. 원본 JSON·캡처와 비교 요약은 [완료된 보고서 실행](https://github.com/obmaz/sjrpg/actions/runs/42396961732)에 보존한다. 보고서는 검증된 두 원본 프로필을 다시 촬영하지 않고 재사용한다. 요약과 단계별 집계는 assets/source/performance에도 보존한다.

수정본의 동굴 후 복귀3회는 텍스처187,091,742B, WASM용량173,670,400B, 노드23개가 동일했다. 기준본도 같은 복귀 단계를3회 반복했을 때 텍스처317,185,446B가 유지되었다. 이 경로에서는 선형 증가를 재현하지 않았으며, 높은 고정 캐시 비용을 줄인 것으로 해석한다. 수정본의 두 번째→세 번째 복귀 사이 JS 힙은2,503,168B 증가했다. 강제 GC 없이 측정했고 관찰 도구도 포함하므로 모든 힙 증가가0이라고 해석하지 않는다. 장시간 물리 기기의 모든 브라우저 충돌을 해결했다는 뜻은 아니다.

수정본은 모든 마을·동굴 단계에서 이전2D 배우 텍스처 로드0개였다. 실제 마을·동굴·가로 화면 캡처에서 모델·재질·HUD 누락이 없는지도 별도 검수한다. CI의 SwiftShader는 소프트웨어 렌더러이므로 그 FPS를 휴대전화 FPS로 보고하지 않는다.

## 반복 비용을 줄이는 구조

- `NativeEnemyModels`: 최초 제작 때 노드 참조가 없는 메시 조립 레시피를 보존한다. 반복 생성은 완성 메시를 공유하고 관절 노드와 변경 가능한 재질은 개별 소유한다. 기존 캐시가 최종 배칭 이후에만 적용되어 발생하던 임시 SurfaceTool 생성을 제거한다. 종별12회 반복 생성에서 SurfaceTool 제작0회, 측정된 반복 생성 평균 약0.34~0.39ms였다. 최초 제작 비용에는 재질/텍스처 초기화가 포함되어 있으므로 이를 순수 메시 제작 전후 속도 배수로 비교하지 않는다.
- 시체는 위치·방향·높이·실제 바닥이 바뀔 때만 배치를 계산한다. 정지 시체60회 갱신에서 재배치0회이며 페이드와 원래 수명은 계속 반영한다.
- `Ortho3DPreview`: 실제3D 버퍼는 긴 변1920px와1,536,000픽셀을 모두 상한으로 사용한다. 절약 모드는 각 축을 절반으로 한다. 화면비·FOV·세계 입력과 UI 해상도는 유지한다. 일반720×1280 및1280×720은 축소하지 않는다.
- 일시정지는 마지막 월드를 한 번 반영한 뒤 SubViewport의 기존 그림을 유지한다. 정지 중 실제 배우/효과/바닥·설정·카메라·크기 변경은 다시 동기화하고, 재개하면 매 프레임 렌더링한다. 실제 프로필의 정지4단계 모두 UPDATE_DISABLED와 동기화 건너뛰기를 확인했다.
- `ClassSelect`: 저장/선택 화면 레이아웃을 매 프레임 JSON으로 만들어 JS에 쓰던 경로를 실제 레이아웃·스크롤·포커스 진입/해제 이벤트로 변경했다. 같은 프레임의 이벤트를 합치고 내용이 같으면 다시 쓰지 않는다. 스크롤 값 변경과 자식 이동 사이의 불일치를 피하도록 한 번의 렌더 완료 후 실제 좌표를 게시한다. 연결된 수신자가 해제되면 일회성 신호 연결도 해제된다. 실제 삭제 팝업의 최종 전역 위치와 스크롤로 이동하는 상위 컨테이너도 관찰한다.

## 회귀와 재현

`actor_atlas_lazy`, `entry_probe_budget`, `native_enemy_recipe_cache`, `native_render_budget`는 각각 숨김/실제 원화 소비, 이벤트 합치기/실제 포커스 해제, 메시·재질 독립성과 시체 바닥 변경, 초고해상도/정지/재개/입력 투영을 검사한다. 일반 전체 검사·실제 저장40/로딩24/패드23 브라우저 경로도 배포 조건으로 유지한다.

`.github/workflows/resource-profile-review.yml`은 고정 기준 커밋과 현재 소스를 각각 내보내 동일한 관찰기·입력으로 측정한다. 관찰기는 worker에서만 Main에 연결하며 일반 운영 진입점에는 포함하지 않는다. `resource_profile_review.gd`와 `resource_telemetry.mjs`는 상태를 읽으며 피해·적·생명·진행을 변경하지 않는다. 텍스처 측정 자체가 lazy getter를 호출하지 않도록 한다.

사용자가 제공한 재현 환경은 갤럭시 폴드8, 설치 앱, 마법사이며 마을 이동 중 앱이 닫히거나 문서가 다시 로드되는 증상이다. 아래 비교는 이 조건의 화면·입력을 모사한 CI 측정이고 실제 기기의 OS 종료 원인을 확정하지 않는다. 헤드리스 종료의 OGG 잔여 참조는 새 오디오 믹스와 메인 루프 정리 완료를 확인하는 테스트 러너로 별도 검증했다. 같은 작업 환경의 기준/실험 비교와 독립3개 빠른 검사·전체109개 검사를 보존한다. 이 테스트 종료 동기화를 웹 브라우저 종료 원인의 해결 증거로 섞지 않는다.


## 폴드 화면의 실제 이동 비교

마을 진입 위치만 반복해서 관찰하면 카메라 이동·새 물체 노출·터치 입력에 따른 비용을 놓친다. `town-walk-review.yml`은 고정 기준 `3f4c9fe347bd58fa2fc2c609671b4de549a1b09b`와 실험 `6a63c301e60055b74beb6a5f990af1cfe8e2e5b4`를 같은 관찰기로 내보냈다. 위치 고정용 `at` 없이 정상 시작한 뒤 WASD/실제 CDP 터치로15초 정지·90초 이동·15초 정지를 수행하고 카메라·물리 틱·플레이어 이동을 함께 확인한다. 체력·시간·몹을 변경하지 않는다.

768×1024 CSS, DPR3, Android·설치 표시 모드의 폴드 모사에서 마법사 고품질의 동일한 첫 위치를 비교한 값이다.

| 항목 | 기준 | 실험 |
| --- | ---: | ---: |
| Godot 텍스처 메모리 | 330,881,312 B | 202,457,512 B |
| 최종 캔버스 | 2304×3072 | 1254×1672 |
| 실제3D 렌더 타깃 | 960×1280 | 960×1280 |
| 숨겨진 IsoSprite 원화 캐시 | 10개 | 0개 |
| WASM 선형 메모리 용량 | 144,703,488 B | 144,703,488 B |

텍스처는 약38.8% 감소했다. 절약 모드에서도303,847,712→175,423,912 B였고 실제3D 렌더 타깃480×640은 유지했다. 이는 다음 두 경로의 고정 비용을 줄인 결과이며 이미지 원본 크기나 게임 모델을 바꾼 결과가 아니다.

- 숨겨진2D 배경의 `IsoSprite`·수면·차양은 설정 시 원화를 읽지 않는다. 실제 그리기 또는 남아 있는 원화 어댑터가 요청할 때만 읽고 필요한 워프 메시를 만든다.
- 모바일의 최종 캔버스에2,097,152픽셀·DPR2 상한을 적용한다. Godot의 `canvasResizePolicy=0`으로 실제 버퍼만 조절하고 CSS 크기·브라우저 DPR·논리 HUD 크기·화면비는 유지한다. 터치 좌표는 실제 캔버스/표시 사각형 비율을 따르며 화면 접기·펼치기 및 전체화면 변경에도 다시 계산한다. 데스크톱은 원래 자동 정책을 유지한다.

실제 비교 실행 [42439171278](https://github.com/obmaz/sjrpg/actions/runs/42439171278)의 양쪽4프로필(마법사 고품질 터치·절약 터치·키보드, 전사 고품질 터치) 모두 이동·카메라 추적·문서 유지·WebGL 컨텍스트 유지 검사를 통과했다. 마법사 고품질 터치는768×1024→390×844→768×1024 전환도 통과했다. 콜드 원화 로딩과24개 관련 회귀는 별도 검사했다.

SwiftShader 실행은90초 동안73~205 렌더 프레임으로 실제 기기보다 느렸다. 이 결과를 휴대폰의90초 프레임 부하나 장시간 충돌 해결 증거로 바꾸어 해석하지 않는다. Chrome 프로세스 PSS는 프레임 수에 따라 여전히 증가했고 실험군에서 일관되게 낮아지지 않았다. Godot 텍스처·살아 있는 GL 저장 공간·JS 힙·WASM 용량·운영체제 PSS는 서로 다른 값이며, 이 측정으로 전체 브라우저 메모리 누수나 실제 기기의 종료 문제가 해결됐다고 확정하지 않는다.


## 대기 중 누적되는 웹 음악 메모리

가만히 있어도 종료된다는 재현 조건으로 정상 시작 위치에서 입력 없이 관찰했다. [동일 대기 비교](https://github.com/obmaz/sjrpg/actions/runs/42449279732)에서 이전 버전과 HUD·미니맵을 유지하는 수정본 모두 약384 렌더 프레임에 Chrome PSS 약6.5GB로 검사 보호 한도를 초과했다. 수정본은 초기 안정화 뒤 새 GL 버퍼·VAO 생성0개였고 JS 힙·WASM 용량·Godot 텍스처도 일정했다. 따라서 UI 재그리기 감소와 높은 고정 텍스처 비용의 절감은 이 누적 종료 원인을 해결한 증거가 아니다.

원인은 `MusicDirector.step()`의 매 프레임 `stream_paused = false` 호출이었다. Godot4.7.2의 [AudioStreamPlayerInternal](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/audio/audio_stream_player_internal.cpp)은 같은 값에도 웹 샘플 pause를 전달한다. [웹 오디오 구현](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/web/js/libs/library_godot_audio.js)의 `pause(false) → _unpause() → _restart() → getAudioBuffer() → _duplicateAudioBuffer()`는 음악 전체를 다시 복사한다. 기존 소스는 연결만 끊으며 정지하지 않고, 기존 ended 콜백도 남을 수 있다.

마을 곡41.739125초를44.1kHz 스테레오 Float32로 재생할 때 한 복사량은14,725,560B(약14.0434MiB)다. 관찰된 약14.026~14.087MiB/렌더 프레임의 증가와 일치한다. [추가 Godot 관찰기를 넣지 않은 실제 배포물 진단](https://github.com/obmaz/sjrpg/actions/runs/42449980110)에서도 같은 증가를 재현했다. 이후의 GPU 완료 대기·GC로 해결되지 않았으며, 이 진단의 네이티브 샘플러/메모리 트레이스는 유효한 할당 스택을 얻지 못했다. 이를 성공적인 내부 할당 프로파일로 해석하지 않는다.

수정본은 긴 음악을 `AudioServer.PLAYBACK_TYPE_STREAM`으로 재생하고 트랙별 포커스 적용값을 기록해 실제 전환에만 pause를 전달한다. 새 재생·정지·장면 분리/재부착은 해당 상태를 초기화한다. 짧은 효과음의 샘플 재생과 음악 교차 페이드는 유지한다. `music` 회귀는120회 정상 처리·중복 포커스 알림·정지·재부착·음악 설정을 검사한다.

`town-stability-review.yml`의 동일 대기 비교는 실제 `Engine.get_frames_drawn()` 1,200프레임, 늦은 메모리 구간, 오디오 버퍼 생성량을 확인한다. 오디오 관찰기는 성공한 `createBuffer`/`createBufferSource`의 수와 PCM 바이트만 세고 버퍼·재생 소스를 보관하지 않는다. 정상 판정 전에 강제 GC를 하지 않는다. 실패한 기준 버전 결과도 그대로 보존하며 실제 기기의 OS 종료 확인과 소프트웨어 렌더러의 측정값을 구분한다.


[수정 음악의 동일 대기 비교](https://github.com/obmaz/sjrpg/actions/runs/42450924455)는 기준 `991d38c`와 수정 `ebb63bd`를 같은 하네스로 실행했다. 기준은 약400프레임에서6GiB 보호 한도를 초과했고, 수정본은 **입력 없이 실제1,200 렌더 프레임과 늦은 메모리 구간 검사 모두 통과**했다. 정상 구간에서 강제 GC를 하지 않았다.

| 항목 | 기준 | 수정 |
| --- | ---: | ---: |
| 큰 음악 버퍼 생성 | 약400프레임에1,097회, 누적16,153,939,320B | 초기부터 마지막까지0회 |
| Chrome PSS | 약6.5GB, 보호 한도 초과 | 늦은 두 구간 중앙값1,049,205,760→1,055,395,840B |
| Godot 텍스처 | 152,953,386B | 152,953,386B 유지 |
| WASM 용량 | 144,703,488B | 144,703,488B 유지 |
| 정상 구간 결과 | 실패를 그대로 보존 | 1,200프레임·자원 구간·화면 캡처·오류0 통과 |

누적 PCM 바이트는 생성한 전체 양이며 동시에 남아 있는 메모리와 다르다. 수정본의 후반 PSS 증가는 약5.9MiB이고 JS 힙 증가 약1.52MiB도 별도로 보존한다. 이 소프트웨어 렌더러 결과를 Galaxy 실기기의 메모리나 프레임률로 바꾸어 보고하지 않는다.

배포의 `music` 브라우저 검사는 일반 내보내기와 실제로 실행되는 AudioContext에서40회 이상의 마법사 동작 갱신 동안 새1MiB 이상 AudioBuffer가 생기지 않는지 확인한다. 기본 고정 비교 외에 폴드 고품질 화면 조건도 지원하며, 검사 자체는 오디오 버퍼·소스를 보관하지 않는다.
